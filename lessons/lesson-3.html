From User Needs to Ready Work

In this lesson, you will turn a broad Student Hub need into work the team can build and test. You will write a user story. Then you will add acceptance criteria so the team knows what success looks like.

Student Hub connection

Clarify the Next Student Hub Need

In Lesson 2, you chose who should lead team decisions. Now the team needs clearer product work.

Students, teachers, and support staff may use Student Hub in different ways. Their needs help the team understand the problem before building.

Use user story and acceptance criteria language precisely so another person can understand the need, test the result, and verify whether the work is ready.

Your final backlog item should be specific enough for a Product Owner to order it, for Developers to build it, and for testers to verify it against observable acceptance criteria.

This precision matters because unclear requirements can create rework, hidden assumptions, and product increments that appear complete but do not satisfy the user need.

When you justify a user story, include stakeholder context, measurable behavior, verification conditions, and accessibility constraints so the Product Backlog communicates development intent without prescribing every technical implementation detail.

LEARN, User needs often begin as broad requests. A software team needs to clarify the need before it builds. A user story is one common Agile practice. It is not an official Scrum artifact.

A common format is: As a [user], I want [goal], so that [benefit]. The user tells who needs the feature. The goal states what the person needs. The benefit explains why it matters.

A strong user story focuses on value. It does not force one solution too early. For Student Hub, the team should understand the student’s problem before choosing a design or code change.

Step 3.3 · Learn and check

Acceptance Criteria Make Work Testable

Estimated time: 10 minutes

▶️ Your next move: Watch for how acceptance criteria help a team decide whether a story is ready to build and complete.

Acceptance Criteria and Agile Scrum Planning

Reinforce how acceptance criteria help a team decide whether a user story is ready and complete.

Open video in new tabOpen transcript

Acceptance criteria describe what must be true for a story to work. Each criterion should be observable and testable. A tester should be able to check it without guessing.

Criteria describe product results, not development tasks. “Build the filter quickly” is not testable enough. “Keyboard users can reach and use the date filter” is testable because someone can try it.

Acceptance criteria also help the team protect access and quality. For Student Hub, the team can include criteria for small screens, keyboard use, clear messages, and correct results.

The Product Backlog may contain user stories, but Scrum does not require that format. Developers use clear backlog items and the Definition of Done to create a usable Increment.

Professional teams avoid vague backlog work because vague work creates rework, missed expectations, and testing confusion.

Acceptance criteria should describe observable behavior, conditions, and results so the team can inspect the Increment against shared evidence.

Add criteria to the Student Hub story

Use the story from Step 3.2. Then write criteria another person can test.

Story
As a student using a phone, I want to scan assignments by due date so that I can plan upcoming work.
Criterion 1
Assignment cards show the course name and due date on a small screen without cutting off the text.
Criterion 2
Keyboard users can move through the assignment list in due date order.
Criterion 3
When no assignments match the filter, Student Hub shows a clear message.
